## 1. システム概要と設計方針

### 1.1 背景と課題
従来のRAGシステムでは、PDFやOffice文書（Word、PowerPoint、Excel）を取り込む際に単純なテキスト抽出ライブラリ（PyPDF、pdfminer等）が用いられていました。これにより、以下の深刻な課題が発生していました：
* **表構造（Table）の崩壊**: セル結合や複数行ヘッダーが平坦化され、LLMが数値と項目の関係性を誤認する。
* **図表・レイアウトの欠損**: 多段組やスライドレイアウトの順序が狂い、文脈が断片化する。
* **グラウンディング（根拠提示）の弱さ**: 取得されたテキストが元文書の「どのページのどの座標」に存在したかを追跡できず、回答の監査・人間による確認が困難。
* **機密性・コストのジレンマ**: 高精度な商用SaaSパーサー（LlamaParse等）は外部送信が必須かつ従量課金が高額。

### 1.2 本システムの目的
本システムは、オープンソースの高度ドキュメント解析エンジン **Docling** と **LlamaIndex** を統合し、以下の機能を提供するオンプレミス/ローカル完結型のREST APIプラットフォームです：
1. **マルチフォーマット対応**: PDF、DOCX、PPTX、XLSX、HTML、CSV等を単一のエンドポイントで共通解析。
2. **表・レイアウト高精度抽出**: 内蔵のTableFormer/レイアウトモデルにより、表構造をMarkdown/HTML形式で正確に保持。
3. **バウンディングボックス（Bounding Box）追跡**: チャンクごとに元文書のページ番号および矩形座標を保持し、画面上でのハイライト表示を実現。
4. **ハイブリッド埋め込み対応**: 完全ローカルの **Ollama** をデフォルトとし、**IBM watsonx.ai**、**OpenAI** をAPI経由でホットスワップ可能。
5. **モデルガバナンス**: 既定モデルは IBM Granite シリーズ（生成 `granite4.2:latest`、埋め込み `granite-embedding:278m`、文書解析 Docling / Granite-Docling-258M）に統一し、中国製の LLM・埋め込み・OCR モデルは使用しない。

## 3. データフロー設計

### 3.1 ドキュメント取り込みフロー (Ingestion Flow)

```
[クライアント]
      │
      │ 1. POST /api/v1/ingest (マルチパートファイル送信)
      ▼
[FastAPI: ingest_document]
      │
      │ 2. 拡張子検証 (.pdf, .docx, .pptx, .xlsx, .html, .csv)
      │ 3. 一時保存 (temp_upload_dir/filename)
      ▼
[DoclingReader]
      │
      │ 4. load_data(export_type=JSON) 実行
      │    - TableFormer: 表のセル・ヘッダー関係解析
      │    - Layout Model: 見出し、本文、図表の境界検出
      ▼
[DoclingNodeParser]
      │
      │ 5. get_nodes_from_documents()
      │    - 構造境界（セクション・表単位）でチャンキング
      │    - 各ノードの metadata に doc_items (prov, bbox, page_no) を格納
      │ 6. メタデータに file_name を追加
      ▼
[VectorStoreIndex]
      │
      │ 7. 設定された Embedding モデル経由でベクトル生成
      │ 8. インデックスにノードを追加 (insert_nodes)
      ▼
[クリーンアップ]
      │
      │ 9. 一時ファイルの物理削除 (unlink)
      ▼
[クライアント]
      ◀── 10. レスポンス返却 (作成ノード数、サンプルプレビュー)
```

### 3.2 検索・回答・グラウンディング生成フロー (Query Flow)

```
[クライアント]
      │
      │ 1. POST /api/v1/query (query, top_k, export_grounding)
      ▼
[FastAPI: query_rag]
      │
      │ 2. インデックス存在チェック
      │ 3. index.as_query_engine(similarity_top_k=top_k) 作成
      ▼
[LlamaIndex Query Engine]
      │
      │ 4. クエリのベクトル化 (Active Embed Model)
      │ 5. コサイン類似度検索による上位 Top-K ノード取得
      │ 6. LLM 呼び出しによるプロンプト合成・回答生成
      ▼
[グラウンディングメタデータ抽出処理]
      │
      │ 7. source_nodes をループ処理:
      │    - node.metadata["doc_items"] を走査
      │    - 各 prov 内部の page_no, bbox (l, t, r, b, coord_origin) を抽出
      │    - GroundedSourceNode オブジェクトを構築
      ▼
[クライアント]
      ◀── 8. レスポンス返却 (回答テキスト + ソースノード + BBox座標配列)
```

### 4.2 ドキュメント取り込み API

#### `POST /api/v1/ingest`

* **Content-Type**: `multipart/form-data`
* **説明**: ファイルをアップロードし、DoclingのAIレイアウトモデルを用いて構造化パースを実行後、LlamaIndexのノードとしてベクトル化します。

##### リクエストパラメータ (Form Data)
| パラメータ名 | 型 | 必須 | 説明 |
| :--- | :--- | :--- | :--- |
| `file` | Binary File | ◯ | 対象ファイル（`.pdf`, `.docx`, `.pptx`, `.xlsx`, `.html`, `.csv`, `.xml`） |

##### レスポンスボディ (`application/json`)
```json
{
  "status": "SUCCESS",
  "file_name": "quarterly_financial_report.pdf",
  "total_nodes_created": 18,
  "active_embedding_provider": "ollama",
  "sample_nodes": [
    {
      "node_id": "7f8b9e64-1a2b-4c3d-8e5f-0a1b2c3d4e5f",
      "text": "3.2 連結損益計算書 当第3四半期累計期間における売上高は...",
      "headings": ["第3章 財務ハイライト", "3.2 連結損益計算書"]
    }
  ]
}
```

##### ステータスコード
* `201 Created`: 正常に取り込みおよびインデックス完了。
* `400 Bad Request`: 未対応の拡張子、または破損ファイル。
* `500 Internal Server Error`: Doclingパースエラー、GPUメモリ枯渇、書き込みエラー。

### 4.3 グラウンディング付きクエリ API

#### `POST /api/v1/query`

* **Content-Type**: `application/json`
* **説明**: ベクトル検索を行い、回答と同時に引用元ファイルのページ番号・矩形座標（Bounding Box）を返却します。

##### リクエストボディ
```json
{
  "query": "2025年度の営業利益率の目標値とその根拠となる施策を教えてください。",
  "top_k": 3,
  "export_grounding": true
}
```

##### リクエストパラメータ仕様
| フィールド | 型 | デフォルト | 制約 | 説明 |
| :--- | :--- | :--- | :--- | :--- |
| `query` | `string` | - | 必須 (1文字以上) | ユーザーの質問文 |
| `top_k` | `integer` | 4 | $1 \le \text{top\_k} \le 20$ | 取得する関連ノードの上限数 |
| `export_grounding` | `boolean` | true | - | Bounding Box座標を含めるか否か |

##### レスポンスボディ (`application/json`)
```json
{
  "query": "2025年度の営業利益率の目標値とその根拠となる施策を教えてください。",

      "file_name": "mid_term_plan.pdf",

        {
          "page_no": 14,
          "l": 72.0,
          "t": 520.4,
          "r": 523.5,
          "b": 480.1,
          "coord_origin": "BOTTOMLEFT"
        }
      ]
    }
  ]
}
```

### 4.4 埋め込みモデル動的切り替え API

#### `POST /api/v1/config/embedding`

* **Content-Type**: `application/json`
* **説明**: ランタイムを停止することなく、Activeな埋め込みプロバイダを切り替えます。


## 5. データモデル・スキーマ仕様

### 5.1 Bounding Box（座標系）仕様

Doclingの出力する座標系は、デフォルトで **左下原点（`BOTTOMLEFT`）** を採用しています。

$$P(x, y) \quad \text{where} \quad (l, b) = (\text{左端}, \text{下端}), \quad (r, t) = (\text{右端}, \text{上端})$$

```
(0, Page_Height) ┌─────────────────────────┐ (Page_Width, Page_Height)
                 │                         │
                 │     (l, t)┌──────┐      │
                 │           │ BBox │      │
                 │           └──────┘(r, b)│
                 │                         │
         (0, 0)  └─────────────────────────┘ (Page_Width, 0)
                  [coord_origin: BOTTOMLEFT]
```

* **Web UI連携時の注意**:  
  HTML5 Canvasや通常のCSS座標系は **左上原点（`TOPLEFT`）** です。フロントエンドでハイライトを描画する際は、以下の変換式を適用してください：
  
  $$\text{Top}_{\text{web}} = \text{Page\_Height} - t$$
  $$\text{Left}_{\text{web}} = l$$
  $$\text{Width}_{\text{web}} = r - l$$
  $$\text{Height}_{\text{web}} = t - b$$

### 5.2 Pydantic データモデル定義

```python
class BoundingBox(BaseModel):
    page_no: Optional[int] = Field(None, description="元文書の該当ページ番号（1-indexed）")
    l: Optional[float] = Field(None, description="左端X座標 (Left)")
    t: Optional[float] = Field(None, description="上端Y座標 (Top)")
    r: Optional[float] = Field(None, description="右端X座標 (Right)")
    b: Optional[float] = Field(None, description="下端Y座標 (Bottom)")
    coord_origin: Optional[str] = Field("BOTTOMLEFT", description="原点位置")

class GroundedSourceNode(BaseModel):
    node_id: str
    text_snippet: str
    score: Optional[float] = None
    headings: List[str] = []
    bounding_boxes: List[BoundingBox] = []
    file_name: Optional[str] = None
```

## 6. 非機能要件・インフラストラクチャ設計

### 6.1 開発環境および依存関係管理
* **ツールチェーン**:
  * **`mise`**: Pythonランタイムバージョンの固定（Python 3.11.x）および環境変数管理。
  * **`uv`**: 超高速パッケージレゾルバ、仮想環境構築（`.venv`）、および再現性のあるロックファイル管理。

### 6.2 ハードウェア要件

| 規模 | 推奨構成 | 処理能力の目安 |
| :--- | :--- | :--- |
| **開発 / 検証** | CPU: 8 Cores / RAM: 16 GB（GPUなし） | PDF 1ページあたり約 1.5 〜 3.0 秒 |
| **本番 (Standard)** | GPU: NVIDIA T4 / A10G (16GB VRAM) $\times$ 1 | PDF 1ページあたり約 0.3 〜 0.7 秒 |
| **本番 (大規模バッチ)** | GPU: NVIDIA L4 / A100 $\times$ 2基以上 | 複数ファイル並列実行（スループット 10倍） |

### 6.3 セキュリティ・機密保持要件
1. **完全エアギャップ・オンプレミス運用**:
   * Doclingパーサー、Ollama（LLM & Embedding）の組み合わせにより、全トラフィックを社内イントラネット内で完結。外部SaaSへのデータ流出を100%防止。
2. **一時ファイルの即時消去**:
   * アップロードされたファイルはパース処理直後に `finally` 句で確実に物理削除（`unlink()`）。
3. **CORS設定**:
   * 本番環境ではワイルドカード（`*`）を廃止し、承認済みフロントエンドドメインのみを許可。

## 7. エラーハンドリング・運用保守設計

### 7.1 主な例外パターンとハンドリング

```
[クライアント要求]
      │
      ├─ [未対応の拡張子] ──> 400 Bad Request ("Unsupported format...")
      │
      ├─ [インデックス未初期化の検索] ──> 400 Bad Request ("No documents indexed...")
      │
      ├─ [ファイル破損 / PDF暗号化] ──> 500 Internal Server Error ("Docling parsing failed...")
      │
      └─ [Ollama 接続タイムアウト] ──> 503 Service Unavailable ("Model server unreachable")
```

### 7.2 ヘルスチェック監視 (`GET /health`)
ロードバランサー（ALB / Nginx）やKubernetesの `readinessProbe` / `livenessProbe` は `/health` をポーリングし、以下のステータスコードを判定基準とします：
* `200 OK`: サービス稼働中（インデックスドキュメント件数、現行プロバイダを返却）。

## 8. 今後の拡張計画

1. **ベクトルDBの外部永続化**:
   * 現在のインメモリ `VectorStoreIndex` から、**Qdrant**、**Milvus**、または **pgvector** への永続化コネクタの追加。
2. **ハイブリッド検索（Hybrid Search）の導入**:
   * Doclingで抽出したテキストに対する BM25 キーワード検索と、Dense Vector 埋め込み検索を **Reciprocal Rank Fusion (RRF)** で統合。
3. **リランカー（Reranker）の追加**:
   * `ibm-granite/granite-embedding-reranker-english-r2` や `cohere-rerank` をパイプラインに挿入し、Top-K精度を向上。
4. **ストリーミングレスポンス (Server-Sent Events)**:
   * 生成回答の First Token レイテンシ短縮のための SSE エンドポイント提供。
